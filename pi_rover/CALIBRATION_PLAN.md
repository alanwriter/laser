# 三車路徑跟隨：地面校正方案

這是下一階段的**一次性校正**，不是每次 3 分鐘試跑都重做。
2026-11-12 三台 Pi 已部署 `0.2.0-dev+left-turn`，F1/F2 都是各自車道的
路徑切線跟隨；三台 Nano 已改純 MPU 航向，Leader 另有開機 MPU 探測重試。
同日左轉實跑已因碰撞與 F2 過遠安全旗標中止，詳見
[`實跑內部訊息`](../analysis/2026-11-12-compact-left-turn/real_run_094329Z/README.md)。
三台車的 Nano 仍保有原有速度控制與安全停止。校正測試應在三車依序、
輪子接地、地面淨空、可即時切斷馬達電源的條件下進行。

## 為什麼先量底層

2026-10-29 第二趟三車實跑的 CSV 顯示：Leader 命令巡航 45 mm/s，
車上里程計在 24.16 s 走出 1504 mm 的 x 進度，約 62.3 mm/s。這是**里程計
估計**，不是真實地面速度。同趟移動期間，Nano 回報的 `left_tps`／
`right_tps` 常高於 `left_target_tps`／`right_target_tps`；Leader 在目標 TPS
大於 20 的樣本中，兩輪的 `measured/target` 中位數約 1.84／1.78。兩台
follower 也有類似現象，但它們常在轉彎與加減速，不能用全程比值直接改 PID。

因此要分辨三件事：**實際地面位移**、**Nano 估計位移**、**Nano 接到的輪速
目標與量到的輪速**。只把 45 乘 `45/62.3` 會把不同誤差混在一起。

## 已找到的韌體幾何與舊校正紀錄

`alanwriter/Arduino-ugv` 的三個 `*-pi-usb` 分支共用 `src/main.cpp`：每輪
`count / ticks_per_mm` 換成距離，取左右平均前進量；航向增量在 IMU 已校正時
為 `0.30 × (右輪距離−左輪距離)/輪距 + 0.70 × gyro-Z 積分角`，再用中點航向
積分 `x/y`。這是**相對里程計**，不會由 MPU6050 直接量到地面平面座標。

| GitHub 車輛 profile | 左／右 ticks 每圈 | 直徑／輪距 |
|---|---:|---:|
| Leader | 1216.4／1222.4 | 65／130 mm，暫定 |
| F1 | 1203.5／1200.0；右輪尚是暫定值 | 65／130 mm |
| F2 | 1216.2／1237.4 | 65／130 mm，暫定 |

來源：`Arduino-ugv` 的 `src/vehicle_profile.h`（`leader1-pi-usb`、
`follower1-pi-usb`、`follower2-pi-usb` 分支）及
`docs/leader1_calibration.md`、`follower2` 分支的
`docs/follower2_calibration.md`。紀錄表示使用者曾確認三車的約 65／130 mm
實體尺寸；**尚未找到接地轉彎測出的有效輪距數值**。既有 700 mm 方形
`G2` 是用來觀察回起點與轉彎誤差的校正測試。F2 於 2026-09-07 曾做
未提交的 100% gyro-Z 航向試驗，方形看來較方正，不能當作目前已部署設定。
套用任何修正前，須核對每車實際燒錄的韌體／`CONFIG`。
2026-11-12 使用者表示 F1 未見卡滯或打滑，認為同 PWM 的馬達速度差是主因；
Nano 的 `MOTOR` 預檢是開環 PWM，`VELOCITY` 則用每輪編碼器 PID。
不應由開環 count 差直接推論卡住，也不能由閉環目標值直接推論實際輪速。
後續試次若操作者觀察到輪胎空轉或車體滑移，標記無效並重做；原始資料仍留存，
但不納入有效試次的曲線、里程比例與控制器比較。有效試次的誤差分析先查各輪
馬達特性、輪速迴路、編碼器／里程換算、初始擺位與影像量測基準，不以打滑解釋。

## 一次布置

1. 固定相機在高處，盡量接近俯視，不要手持。地面貼至少四個不共線的已知
   座標點，例如 `(0,−500)`、`(1500,−500)`、`(0,+500)`、`(1500,+500)` mm；
   用尺量點與點的**實際**距離。畫出每台車的起點、前進 500 mm 終點和安全區。
2. 每車在 MPU6050 正上方貼一個俯視可辨的座標標記，另貼車頭方向標記，
   以 **MPU 點**作位置，與 CSV 的使用者定義一致；斜視相機還須校正標記高度
   導致的視差。影片要
   同時看到四個地面點、車身和停止時刻。把相機畫面做透視校正後才換算 mm。
3. 每台車保留原始 Nano `CONFIG`、韌體版本／映像及 Pi 程式雜湊。Nano 原始碼在
   另一個 GitHub 專案 `alanwriter/Arduino-ugv` 的 `leader1-pi-usb`、
   `follower1-pi-usb`、`follower2-pi-usb` 分支，主要是 `src/main.cpp` 與
   `src/vehicle_profile.h`；仍須核對各車實際燒錄版本，不能只憑分支內容
   假定實車設定或直接寫入硬體。

## 最短的分段測試

先做 **Leader 一台**；如果第一階段發現明顯比例錯誤，先查清楚再量 F1/F2，
避免重複無效的三車實跑。
Leader 上新裝的 RPLIDAR S3 可在固定環境中記錄掃描與 Nano 里程計，
但在確認 USB、掃描率與同時運作之前，不能代替下表的實際地面量測；
Leader 的掃描定位也不會自動校正 F1/F2 的位置。

| 階段 | 每車動作 | 同時記錄 | 要辨別的問題 |
|---|---|---|---|
| 靜止 | 車體不動完成 IMU 校正、RESET，再靜止 10 s | 畫面方向、`heading_deg`、故障旗標 | 靜止漂移或起點方向錯誤 |
| 直線 | 低速 500 mm，先用 25 mm/s，再用 45 mm/s，各一次；每次回起點重新 RESET | 影片地面距離／時間、CSV `x_mm`、兩輪 count、TPS 與 target TPS | 里程計比例與速度控制是否各自正確 |
| 轉向 | 低速左／右各約 90° 的短弧，各一次 | 影片實際航向、CSV 航向、左右 count | 左右輪不對稱、有效輪距或 IMU 航向偏差 |

## 如何判讀與調整

對每段直線計算：

```text
位置比例 R_pose  = Nano 位移 / 影片地面位移
速度比例 R_speed = 影片地面位移 / 實際運動秒數 / 輪速命令
輪速比例 R_tps   = 穩態 measured TPS / 同時的 target TPS
```

TPS 只取指令維持不變、車已穩定加速後的至少 1 s 區間；排除起步、煞停、轉彎。

- `R_pose` 偏離 1、`R_speed` 接近 1：優先校正 Nano 的 count→mm 換算／輪徑。
- `R_pose` 接近 1、`R_speed` 偏離 1，且 `R_tps` 同方向偏離：優先查 Nano
  的速度迴路、PWM 最小值、TPS 取樣與目標更新時序。
- 左右 count/TPS 或直線航向不對稱：先分清開環同 PWM 馬達差異與閉環
  `measured/target TPS` 差異，核對每輪編碼器換算；再用左右轉的實際角度
  估計有效輪距。不要先改路徑控制增益掩蓋底層差異。
- 轉彎影片角度與 IMU 航向不符：先檢查靜止校正、安裝方向、磁／振動干擾及
  輪速與編碼器記錄，再改姿態估計；若該趟觀察到打滑，依上述規則排除重做。

暫定通過門檻：500 mm 直線的地面距離與 Nano 位移差不超過 5%，穩態地面
速度與命令差不超過 10%，直線航向偏差不超過 5°；左右轉的實際角度與
車上航向差不超過 5°。這些是下一次調參的工程目標，不是這趟影片已證明的精度。
通過後再以雙路徑控制器跑三車，量各車的地面橫向誤差與 400 mm 路徑進度差。
